# Build variants

Session ships in several builds that differ in what they can do: which push service they talk to,
whether Pro can be bought in the app, whether a store updates them. Each build reports a **variant**,
and shared code asks the variant's **traits** rather than its name, so a screen says "is there a push
service?" and never "is this Play?".

The list and the traits are `BUILD_VARIANTS` and `VARIANT_TRAITS` in
[`packages/app/src/buildVariant.ts`](../packages/app/src/buildVariant.ts), and `buildTraits()` in
`buildTraits.ts` gives the running build's. The variant is `ports.build.variant`, and the logs'
header prints it as **Variant**.

## The variants

| variant       | platform | how the app knows                | push service | Pro purchase | rating prompt | checks for updates |
| ------------- | -------- | -------------------------------- | ------------ | ------------ | ------------- | ------------------ |
| `play`        | Android  | built as the `play` flavour      | Google       | Play         | yes           | no                 |
| `fdroid`      | Android  | built as the `fdroid` flavour    | none ¹       | no           | no            | no                 |
| `website`     | Android  | built as the `website` flavour   | none ¹       | no           | no            | yes                |
| `huawei`      | Android  | built as the `huawei` flavour    | Huawei       | no           | no            | no                 |
| `appStore`    | iOS      | no embedded provisioning profile | Apple        | App Store    | yes           | no                 |
| `testFlight`  | iOS      | a profile that names no devices  | Apple        | App Store ²  | no            | no                 |
| `adHoc`       | iOS      | a profile that names devices     | Apple        | no           | no            | no                 |
| `development` | iOS      | a Debug build, or the simulator  | Apple        | no           | no            | no                 |
| `euWeb`       | iOS      | not reported yet ³               | Apple        | not yet ³    | no            | yes                |
| `marketplace` | iOS      | not reported yet ³               | Apple        | not yet ³    | no            | no                 |
| `desktop`     | desktop  | always                           | none         | no           | no            | yes                |
| `unknown`     | any      | the build could not say          | none         | no           | no            | no                 |

1. **No Google code at all**, unlike legacy's `fdroid` flavour, which links Firebase Messaging: F-Droid's
   own repository accepts only fully open-source builds. Without a push service, notifications come
   from polling. The website build follows the same rule for now.
2. TestFlight buys through the App Store's sandbox, as legacy's does.
3. Apple's `AppDistributor` (MarketplaceKit, iOS 17.4 and later) can tell an install from the web
   or an alternative marketplace apart from the App Store, but it is asynchronous and the variant
   is read synchronously at launch. Until that is wired up, or the EU build is marked when it is
   exported, such an install reports as `appStore`. TODOs in `buildVariant.ts` say what each of
   these still needs.

A push service named here is the one a build would talk to, not one it does: fast mode also needs
registration with that service, which does not exist yet, and on Android a device that has the
service (Google Play Services or microG, or HMS Core), which is asked at runtime.

## Android: one flavour per store

The four flavours are Gradle product flavours, added to the generated `app/build.gradle` by
[`apps/mobile/plugins/withBuildVariants.ts`](../apps/mobile/plugins/withBuildVariants.ts), since the
native project is generated by `expo prebuild` and not committed. All four keep the same application
id, as legacy's do, so moving between stores that sign with different keys means uninstalling.

Each flavour writes its name into the manifest (`org.getsession.BUILD_VARIANT`), and
`modules/session-logs` reads it back at launch. Read from the APK rather than from Metro, so one dev
server serves any of the four.

Library code that only one flavour may link (Firebase in `play`, HMS in `huawei`) goes in that
flavour's dependencies, so a build without the service never contains it.

```sh
pnpm android                                                     # play, Debug
cd apps/mobile && npx expo run:android --variant websiteDebug    # any other: <flavour>Debug|Release
cd apps/mobile/android && ./gradlew assembleHuaweiRelease        # without the Expo CLI
```

The APKs land in `app/build/outputs/apk/<flavour>/<buildType>/`.

## iOS: one build, told apart at runtime

App Store and TestFlight installs are the same binary, promoted rather than rebuilt, so nothing
baked in could separate them. `modules/session-logs` asks, in order:

- a Debug or simulator build is `development`;
- no embedded provisioning profile is `appStore`, since the App Store strips it;
- a profile that names the devices it may run on (or all of them) is `adHoc`;
- any other profile is TestFlight's App Store distribution profile, so `testFlight`.

Legacy tells the last two apart by the sandbox receipt, which an ad hoc build can name too and so
pass for TestFlight; that is kept only for a profile that cannot be read.

`ports.build.variant` carries the answer to JavaScript like any other variant, so shared code can
tell App Store, TestFlight and ad hoc installs apart.

## Desktop

Always `desktop` for now. Which packages update themselves and which a store or a package manager
updates is to be decided with the desktop packaging.

## Seeing another variant

`EXPO_PUBLIC_SESSION_BUILD_VARIANT` overrides what the build reports, on all three platforms, with
any name from the table: how to see the Huawei description of fast mode on a Play build, or the
screens a build without store purchases shows. A name that is not a variant is ignored, as a
flag's is. A release must never set it.
